Serving this project to devices on your LAN
==========================================

How it works here
-----------------

app.py is a Flask application. Flask maps "/" to the HTML page in
templates/index.html, serves the JavaScript and CSS from static/, and provides
the checklist JSON endpoints under /api/. The browser loads the page and makes
requests back to the same server for checklist operations.

When app.py is run directly, main() starts the Waitress production WSGI server;
it does not use Flask's development server. The bind address is read from
WEB_HOST and the TCP port from WEB_PORT. If neither is configured, this code
uses 0.0.0.0 and port 8081. The repository's documented deployment config uses
WEB_PORT=8787, so use the port actually set in the server's .env file. The app
loads that .env from the project directory, not from the shell's current
directory; shell environment variables can override its values.

0.0.0.0 means listen on all IPv4 network interfaces, including the LAN
interface. It is a server-side bind address, not the address to type into a
browser. On another device, open:

    http://<server-LAN-IP>:<WEB_PORT>

For example, if the server's LAN address is 192.168.1.25 and WEB_PORT is 8787,
use http://192.168.1.25:8787. The server and client device must have a network
route to each other. A host firewall must allow the chosen TCP port from
trusted LAN and/or Tailscale clients. Listening on all interfaces alone does
not configure the firewall or make the service reachable from outside the
network.

The app has no login or application password. Anyone who can reach the port
can view and change the checklist. Permit access only to trusted clients;
do not expose the port to the public internet or set up public port forwarding.
If access should be limited to a particular interface, configure WEB_HOST to
that interface's server-side IP instead of 0.0.0.0, and still apply appropriate
firewall rules.

For the documented Linux deployment, systemd runs app.py using the project's
virtual-environment Python and restarts it after failures. The unit sets the
working directory and loads the production .env file. After starting the
service, check its status and logs, confirm the port in .env is allowed by the
firewall, and test the app locally on the server before connecting from another
device. A local HTTP test can use:

    curl --fail http://127.0.0.1:<WEB_PORT>/api/checklist

What an agent should do for another project
-------------------------------------------

1. Inspect the other project's framework, entry point, frontend/static-file
   setup, dependency manifest, and deployment conventions. Determine how it is
   currently run; do not assume a development server is suitable for ongoing
   use.
2. Choose a server appropriate to that framework and install or declare only
   the required dependencies. Make the app listen on a configurable host and
   port. For LAN-wide listening, bind to 0.0.0.0 for IPv4 (or the appropriate
   IPv6/interface configuration); do not use 127.0.0.1, which accepts only
   connections from the server itself.
3. Keep the port configurable through the project's established configuration
   mechanism. Document its default and how operators override it. Load
   project-local configuration from a stable project path, not an
   unpredictable process working directory, and keep secrets out of source
   control.
4. Provide a persistent process setup consistent with the target host (for
   example, a systemd service on Linux). Run with the intended user, working
   directory, runtime environment, and restart/logging policy. Do not silently
   replace an existing service or add a second competing process manager.
5. Restrict the host firewall to the intended trusted LAN/Tailscale clients
   and chosen TCP port. If the application has no authentication, state that
   clearly and do not expose it publicly. Binding to a LAN interface is not a
   substitute for firewall restrictions.
6. Document how to find the server's LAN address and the browser URL, including
   the port. Explain that clients need network connectivity to the server and
   that the server-side bind address is not the browser destination.
7. Verify in stages: check the service and logs; request a harmless page or
   health endpoint locally on the server; then test from an authorized second
   device. Confirm that an unauthorized network path is not opened as part of
   the change. Use non-destructive tests and avoid endpoints that trigger real
   external actions.

For this project, the implementation to consult is app.py, and the Linux
service and operational commands are in deploy/systemd/nightly-checklist-web.service
and README.md.
